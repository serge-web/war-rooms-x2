# Phase 3 security review notes (internal)

For the tech-lead review of WP 3.5 in the v1 security review (WP 3.4). Not for the public site (DOC-2). Earlier phases' notes, and the findings F1 to F14 they refer to, are in `phase-2-security-notes.md`.

## WP 3.5, objectives by the admin only (D21, §3 rule 14, R10)

- **Who publishes.** `targetState` (`packages/admin-ops/src/target.ts`) and the mock's seed give every White Force role, observer or not, `member` (read) on every `objectives:<forceId>` node, and no role `publisher`. The admin, the node's owner, is the only publisher. `OBJECTIVES_MAX_ITEMS` is 1: the admin's single item, id `admin` (`OBJECTIVES_ITEM_ID` in `@wrx/domain`), replaced on each edit. This reverses the Phase 2 rule that let White Force roles that are not observers publish their own items; F5 (White observers never publish) is now a special case of it.
- **A server published before WP 3.5** holds White Force editors' `publisher` affiliations and their own items, on nodes keeping 10 or more. The next publish corrects it, in this order (`packages/admin-ops/src/publish/plan.ts`):
  1. `node:objectives:<id>` sets `max_items` to 1 (ejabberd may then drop items itself; nothing relies on which);
  2. `grant-node:objectives:<id>` sets each editor to `member`, so from here it can neither publish nor overwrite;
  3. `purge:objectives:<id>`, a new AdminOps step (`AdminOps.purgeNode`, XEP-0060 §8.5 owner purge), deletes every item and then reads the node back: an item left fails `verify-failed`. It is planned for any objectives node holding an item the design does not (`stray`), so it also removes objectives text deleted from the draft, which the old `objectives-kept` warning only reported;
  4. `doc:objectives:<id>:admin` publishes the admin's item again, even when unchanged, since the purge took it.
  Steps 2 to 4 are in the access, then documents groups, so the order holds by construction (plan test "takes the White Force editor's publisher affiliation, then purges, then republishes"). Subscribers hear the purge as a `deleted` event, then the new item.
- **Interface change, for the gate:** `PubsubApi.purgeNode(node)` in `@wrx/transport`, implemented in `transport-xmpp` (StanzaJS `purgeNode`), the mock (`pubsub.purgeNode`, owner only, notifies subscribers), the wire schema (`mock-host`) and the fake.
- **The purge is not a confirmed step.** It deletes the admin's own item too, but the next step puts it back from the design, and what else it deletes is text nobody may publish any more. If the publish stops between the purge and the republish, the force sees no objectives until the re-run (which plans the publish again); it never sees stale text. The step is marked destructive in the plan's `risk` but not in `stepConfirmation`.
- **Readers** (`packages/domain/src/store.ts`) take the admin's item only (`shownItem`), so a stale editor's item on an uncorrected server is never shown, whatever its stamp. The F11 rule still holds: a fetch that answers after a live notification never replaces the item that notification brought (`touched`), and between live events arrival order decides, not `updatedAt`. Tests: `store.test.ts` "F11: a live notification beats the fetched copy, whatever the clock says" (three cases) and "shows the admin's item only, never a former White Force editor's". With one publisher, the F11 residue (a fresh read trusts the stamp) no longer applies: one item has nothing to be ordered against.
- **The client.** `canEditObjectives` is true for the admin alone (`Me`), so the force panel offers no editor to any role, White Force non-observers included, and `publishObjectives` refuses them before sending. The admin's preview as a role is read only for every role. The server refuses them anyway (no publisher affiliation): this is advisory UI over an enforced rule.
- **Audit (ADM-41).** A White Force role left as publisher is a critical `node-access` item (the existing diff against the target), repaired to `member`. Items that are not the admin's are a new `stray-items` item, medium (the game client hides them, other XMPP clients of the force's roles read them), repaired by the planner's purge then publish; `repairRank` puts every purge before every publish, so a repair can never purge the item it has just published. Not destructive, as above.
- **Tests on both backends.** Contract S02 (mock and ejabberd): "the umpire reads both forces' objectives but cannot publish them"; "the owner purges a node after a publisher becomes a reader (D21)": the publisher's item is accepted while it is a publisher, refused once it is a member, the purge leaves no item, keeps the node's config and the member affiliation, and notifies a subscriber once; "a player cannot purge a node". The publish scenario (mock and ejabberd) step 2 builds a pre-WP 3.5 server (White Cell a publisher, `max_items` 10, its own item published, so the node holds `admin` and `white-cell`), publishes, and checks the plan's order, that only `admin` is left with the design's text, that White Cell is refused for both item ids, and that a second publish plans nothing. The admin-ops scenario checks a fresh publish gives White Cell read only. The audit scenario injects the same drift on `objectives:white` and checks the two items, the repair and the effect.

## WP 3.5, GUID ids, login names and deleted-entity records (§3 rule 1)

- **Two names for a role.** `roles:<guid>` holds the role's GUID (`id`) and its `loginName`, the XMPP account's localpart. Everything the server enforces is by account, so in `@wrx/admin-ops` (target, planner, executor, audit, AdminOps, the vault and the credentials book) a "role id" is the login name; `targetState` maps GUID to login name once (`TargetState.loginNames`) and nothing below it sees a GUID for a role. Rooms and nodes carry GUIDs: `rooms:<guid>`, `<guid>@<muc>`, `objectives:<force guid>`. A review should check that no code path builds a JID from a role GUID (it would name an account that does not exist, failing closed) or keys access by login name where the design keys it by GUID (effective access is by GUID, mapped once).
- **The client finds its own role by login name** (`SessionStore.ownRole`), from the role documents it can read; `Identity.loginName` replaces `Identity.roleId`. Message authors are resolved by the occupant JID's localpart (login name), never the body (§3 rules 3 and 6). If node listing fails the client no longer finds its role (before, it read `roles:<its id>` directly); it shows no rooms rather than guessing. Two role documents claiming one login name: the design check refuses it; the client would take the first in display order.
- **Login name rules** (schema, `checkDesign`, the draft, AdminOps): a slug, not `admin` or `anonymous`, not all digits and 16 or more long (F4, `ANONYMOUS_LIKE_NAME`, now applied to login names), unique in the design, and never one a `retired` record holds. The draft fixes a login name once the role is published (`publishedRoleIds`, set by a publish or by the server's plan showing the account); an imported design can still carry a changed one, which the planner treats as a new account plus a deleted one, with a re-sync warning naming both (ejabberd cannot rename an account). Not a confirmed step beyond the usual role-deletion tick.
- **`retired`** is a singleton whitelist node, every role `member`, the admin owner and only publisher, `max_items` 1000 (`RETIRED_MAX_ITEMS`, accepted by ejabberd 26.09, verified by `ensureNode`). One item per deleted force or role, item id the entity's GUID: `{id, kind, name, loginName?, colour?, deletedAt}`. It is published in the documents group, so before the removals group deletes the role's access and account (ADM-39 order: record, affiliations, subscriptions, account; publish scenario step 3 on mock and ejabberd). Where it comes from: the draft records a published role or force it deletes; the planner adds a record for any published role or force the design no longer has and nobody recorded (a safety net, `withRetiredRecords`); the publish screen merges the server's records back into the draft, so their login names are never offered again. Records are never purged or deleted by publish (only a reset deletes the node).
- **Effective access never reads `retired`**: it is not a force, role or room document, the store keeps it apart (`retired()`, used by `authors()` only), and `targetState` grants nothing from it. Tests: `store.test.ts` "never reads `retired` for access", `target.test.ts` "keeps the deleted entities' records in `retired`", `plan.test.ts` "never lets a retired record grant access".
- **Content.** A record holds a display name and a colour that were already readable by every role (role and force documents are read by all game users), so `retired` widens no one's reading. The `deleted` marker in the chat comes from the store's author table, never from a message.
- **Node names (ADM-42).** Names now carry GUIDs only, so an anonymous session listing nodes learns how many forces, roles, rooms and assets exist (it could before), not their names; the audit's notice and the editor say so. `templates` is reserved (`RESERVED_NODE_NAMES`): no prefix or singleton may take it, and the tooling never lists, creates, configures or deletes it or anything under it (`isGameNodeName`).
- **Nodes and rooms from before GUIDs.** `isGameNodeName` accepts `<prefix>:<slug>` as well as GUIDs, and room localparts are any slug, so a reset (ADM-15) finds and removes a game published with slug ids. There is no in-place migration of a server (merge record N3): export, import (which converts), reset, publish.
- **Ids.** `newEntityId()` uses `crypto.randomUUID()` where available and a version 4 GUID from `crypto.getRandomValues` otherwise (plain-http file hosting, NFR-8); ids are not secrets and nothing relies on their unpredictability.

## WP 3.5, migration

- **Design files** (ADM-16): `designFileSchema` is version 2; `readDesignFile` reads version 1 through `convertDesignV1` (`packages/schemas/src/legacy.ts`), which gives every force, role, room and asset a new GUID, rewrites every reference, keeps each role's old id as its login name, and re-checks the result with the version 2 schema and `checkDesign`. A version 1 file with a `password` is still refused. An unknown reference stays unknown (it gets a GUID nobody has), so the check reports it rather than the conversion hiding it. The import warns that the file was converted and that a published game moves by reset and publish.
- **The admin's stored draft** (format version 2) converts the same way on load; roles it had published stay published by their new ids (so their login names stay fixed while the old server still has those accounts). A draft that cannot be read is reported and replaced, as before.
- **The mock's browser database** is version 2; a version 1 state is not migrated (no migration is registered), so the host resets to the seed with its `reset-unreadable` notice (DOC-17). Nothing of the old state is read.
- **Saved layouts** are keyed by the role's GUID, so a layout saved under the old role id is not found and the default is used once (PLY-5). **Multi-client presets** store login names (the old role ids), so they keep working unchanged.
- **Real servers**: none migrated in place (N3). Reset now also finds slug-named nodes and rooms (above). Room history is lost by design; no v1 game has run.
