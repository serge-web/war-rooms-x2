# Phase 2 security review notes (internal)

For the tech-lead review of WP 2.1, 2.3 and 2.10 before the Phase 2 PR merges. Not for the public site (DOC-2).

## WP 2.1, admin operations (`packages/admin-ops`)

- **Vault scope.** The vault holds the password of every read-only role, observers and roles with a per-room read-only entry, because each needs its voice revoked through its own login.
- **Failing closed.** Making a role read-only first takes its membership away in every target room where it is a member, before the vault check and the role's login. Then, room by room, membership and voice revocation run back to back. If revoking voice or the rejoin check fails, the role's membership of that room is removed (`rolledBack`), and the other rooms are still handled. Every failure is reported (`failures`). An observer can lose read access rather than keep voice. Fixed after the G2 review (F1): before, a refused login, a missing vault password or a failure in an earlier room left a writer voiced.
  - Cost: a read-only role that is already a member (a re-check, or an audit repair) has its online sessions ejected from those rooms (status 321) and has to rejoin.
- **Grant-to-revoke window.** The role session is opened and the admin joins before membership is granted, so the window is one join plus one `setRole` round trip. Another online session of the same observer that joins inside that window gets voice. The role's presence briefly shows in the room.
- **Read to write without a vault password** uses an affiliation round trip (none, then member), which ejects that role's online sessions with 321.
- **The `from` hint is required for read-to-write;** without it a stored visitor role stays. The 2.10 audit must catch a missing hint.
- **Vault crypto:**
  - PBKDF2-SHA-256, 600,000 iterations by default, bounded between 100k and 10M on unlock;
  - AES-GCM with a fresh IV per save, and the envelope header bound as additional data;
  - the key is non-extractable;
  - passphrases are NFC-normalised, with at least 12 characters;
  - plaintext passwords stay in JS memory until `lock()`.
- **Concurrent vault edits:** a re-read before each write catches most, but a read-then-write race remains between two admin tabs.
- **Order of password writes:**
  - `setPassword` writes the vault first, then the server, and restores the vault if the server refuses;
  - `createAccount` with `readOnly` creates the account first, then the vault entry, and deletes the account if the vault write fails.
- **Guards:**
  - the `admin` account and other reserved ids are refused by every role operation;
  - node names must parse;
  - destructive account operations refuse while a stored vault is locked.
- **ejabberd quirk:** `getRoomConfig` on a missing room creates the room, so existence is checked by listing rooms first. The mock answers `item-not-found` instead, a known divergence with no contract test yet.

## WP 2.3, publish and provisioning (`packages/admin-ops/src/publish`, `packages/admin-ui/src/publish`)

- **Passwords:**
  - `CredentialsBook` is never persisted, and throws if anything serialises it. Passwords stay in JS memory for the admin's session.
  - Disposal locks the vault and clears the book when the connection or store changes, or `AdminApp` unmounts.
  - Generated passwords are 16 characters from an unambiguous alphabet, about 79 bits, using WebCrypto with rejection sampling.
- **Demo passwords** are issued only when the connection is `kind: 'mock'`. `apps/web` sets it from `backendId === 'mock'` (`apps/web/src/seams/AdminApp.tsx`); check that a real server can never reach that path.
- **The vault passphrase** lives only in the dialog's state. Iterations are the 600k default unless a test sets them.
- **The publish marker** is in localStorage, keyed by server. It holds only `{designVersion, startedAt}`, and an unreadable value makes the planner re-check rather than skip.
- **Password resets:**
  - the planner can schedule a reset when a role becomes read-only and the vault lacks its password, behind a confirmation tick (current sessions stay logged in, PLY-31);
  - an account that already exists is never reset by a create. The planner reads the registered accounts and creates only missing ones; an existing account the server shows nothing else for gets an `account-exists` note, and its password is changed only by an explicit reset (the vault-driven reset above, or the credentials sheet). A create that meets an existing account fails `exists`. Fixed after the G2 review (F3): before, its password was set silently.
- **Destructive scope:**
  - MUC rooms not in the draft are destroyed (D11: one game per server), always behind a message count and a tick;
  - roles inferred from stray affiliations are deleted;
  - anonymous subscriptions on open nodes are deliberately ignored.
- **Import** is schema-checked, refuses passwords, and is capped at 20 MB.

## Fixed during integration

- **`transport-xmpp`:** XEP-0049 private storage worked for only one key per session, because StanzaJS resolves every element defined on the same path to the last one. Every key is now in one JSON object inside one element.
  - It read, then updated, then wrote, so two sessions writing at the same moment could lose an update. Replaced after the G2 review (F14): each key now has its own element on its own path, see below.
  - A new contract test (two keys kept apart) fails on the old code and passes on ejabberd and the mock.

## G2 security review resolutions

The G2 review's findings (internal), and what was done about each. Regression tests are named in each entry; each failed before its fix.

- **F1 (high), a write-to-read conversion failed open. Fixed.** `readOnlyIn` takes the role's membership away in every target room where it is a member before the vault check and the login, then grants and revokes voice room by room. It carries on after a room fails, and reports every failure (`AdminOpsError.failures`, plus a `failed` progress event each). `applyRoomAccess` likewise runs every change and reports every failure. The 2.10 repair order (room config before voice) is unchanged. Tests: `ops.test.ts` "R-B: write to read fails closed"; the integration scenario "a writer made read-only fails closed when the vault has no password for it" runs on the mock and ejabberd. Remaining: if taking the membership away is itself refused, the role keeps it; that failure is reported, and the audit catches it.
- **F3 (medium), silent password resets of existing accounts. Fixed.** `ServerView.registered` holds the XEP-0133 registered accounts. The planner plans `create-account` only for a role whose account is not listed; an existing account the server shows nothing else for gets a non-confirming `account-exists` warning and keeps its password. A reset stays its own destructive step with a confirmed `password-reset` warning (a read-only role the vault has no password for) or the credentials sheet's per-role reset. The executor's `create-account` no longer falls back to `setPassword`: an existing account fails `exists`. So the audit's `account-missing` repair can no longer reset a password, and its `destructive: false` is now accurate. Tests: `plan.test.ts` "accounts against the registered list", `execute.test.ts`, `run.test.ts` "an account-missing repair never resets an account that exists" (the PoC), and the publish scenario's part-way failure re-run (mock and ejabberd).
- **F4 (low), the anonymous-session filter could hide a role account. Fixed in the schema, not the filter.** All-digit role ids of 16 or more characters are now reserved (`ANONYMOUS_LIKE_ID`, `isReservedRoleId` in `@wrx/schemas`): `checkDesign` refuses them, `AdminOps` refuses them like `admin` (`invalid`), the planner and audit never take such a localpart for a role, and the draft prefixes a generated id (`role-1234567890123456`). The transport's `/^\d{16,}@/` filter is unchanged and is now unambiguous. Why this and not passing known role ids into the filter: it is three small checks, while the other route changes the `AdminApi` contract on every transport (xmpp, mock, fake) and still depends on every caller passing the right list; no plausible role name is 16+ digits. Tests: `design.test.ts`, `ops.test.ts` "refuses a role id that looks like an anonymous session", `draft.test.ts`. The audit's offline-account case is unchanged: such an account shows as `account-unknown`, not repairable. Not done: `listOnline` past 1,000 sessions (F10, deferred).
- **F9 (low), confirmations enforced only in the UI or self-reported. Fixed.** `executePlan` takes a required `confirmed` set and, before running any step, refuses the whole plan (`not-confirmed`, nothing run) if a step needs a confirmation that is missing. Which steps need one is worked out from the action alone (`stepConfirmation`: deleting a role, destroying a room, resetting a password), using the same keys as the apply dialog's tick boxes (`confirmationKey`); the dialog now hands the ticked keys to the controller. `repairItems` works out destructiveness from the actions too (`isDestructiveItem`: `delete-role`, `destroy-room`, `delete-node`, `reset-password`, as well as the item's flag), and the audit's builder sets each item's `destructive` the same way, so the UI offers a tick box for it. Behaviour change: the `stray-access` repair (`delete-role`) is now destructive and needs a tick, which also covers F4's "make it destructive when an account could exist". Tests: `execute.test.ts` "confirmations are enforced by the executor", `run.test.ts` "works out destructiveness from the actions". Not covered: `delete-node`, read-only conversions and access revocations are destructive in the plan's `risk` but carry no confirmation, as before.
- **F8 (low), Markdown rendering. Fixed.** One sanitiser (`renderMarkdown` in `@wrx/ui`) serves player views and the admin preview, which now imports it, so the preview shows what players see. Raw HTML stays escaped and images dropped; forms, inputs, media, SVG and MathML are forbidden; `class`, `id`, `name`, `style` and `srcset` are stripped; a link keeps its `href` only for an absolute `http:`, `https:` or `mailto:` URL and gets `target="_blank" rel="noopener noreferrer nofollow"`. The hook lives on a private DOMPurify instance made per call, so the default instance is untouched. Tests: `packages/ui/src/markdown.test.tsx` (links, protocols, class/id, instance isolation) and `packages/admin-ui/src/components/markdown.test.ts` (preview equals the player rendering; raw `<img>`/`<form>` shown as text). Chat stays plain text (PLY-14).
- **F13 (low), `ws://` accepted in config.json. Fixed.** `parseConfig` refuses a `ws:` endpoint (written as `ws:`, or a path or `http:` URL on a plain-http page) unless the host is this machine (`localhost`, `*.localhost`, 127.0.0.0/8, `[::1]`), with the message "server.websocketUrl must use wss: (TLS); plain ws: is allowed only to localhost or 127.0.0.1, not <host>". The refusal is reported like any invalid config.json and the mock is used. Local test stacks (`ws://127.0.0.1:…`) keep working. Test: `apps/web/src/app.test.ts` "refuses plaintext ws: except to this machine".
- **F14 (medium, added after the review), private storage lost concurrent writes. Fixed.** `setPrivate` read the one shared JSON object, changed one key and wrote it all back, so two admin sessions (two tabs, multi-client panes) writing the vault and the publish marker at once could drop one; losing the vault forces password resets. Each key now has its own XEP-0049 element (`<store xmlns='urn:wrx:private:1:<key>' v='1'>`), defined on its own StanzaJS path (`iq.privateStorage.wrx_<hex of key>`), which avoids the same-path alias bug that forced the shared object; the server replaces only that element on a write, so writes of different keys are independent. `v='1'` tells a cleared key from one never written this way; such a key is read from the old shared object, so values stored before the change still read until written again. Concurrent writes of the same key are still last-writer-wins; the vault's re-read before each write (`vault-conflict`) still covers two tabs editing the vault. The mock already stored per key. Tests (contract suite, mock and ejabberd): "private storage keeps concurrent writes of different keys by two sessions" failed on ejabberd before the change (a key's value was lost in round 0) and passes after; "private storage still reads a value from the old shared object" (ejabberd, raw); "private storage keeps several keys apart" still passes.
- **F7 (hardening), no Content-Security-Policy. Added.** `vite build` puts a CSP `<meta>` first in `index.html` (`contentSecurityPolicy` in `apps/web/vite.config.ts`; the dev server is left alone, since it needs an inline React refresh preamble): `default-src 'self'; script-src 'self'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src …; object-src 'none'; base-uri 'self'; form-action 'none'`. No `'unsafe-eval'`, no inline script. `'unsafe-inline'` stays for styles (React style attributes, FlexLayout, styles copied into popouts). `connect-src` is `'self'` in the mock-only build; in the server build it is `'self' wss: ws://localhost:* ws://127.0.0.1:* ws://*.localhost:*`, because `config.json` names the endpoint at run time, so no host can be fixed at build time; plain `ws:` matches F13's loopback-only rule. `deploy/README.md` gives the header form, narrowed to the real `wss://` host, with `frame-ancestors 'self'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. `popout.html` has its own static policy with `script-src 'none'` and `connect-src 'none'` (the opener renders into it). zod's `new Function` probe raised a `script-src eval` violation under the policy; `@wrx/schemas/jitless` sets `z.config({ jitless: true })` and is imported first by `main.tsx` and the mock's SharedWorker. Tests: `apps/web/e2e/shell.spec.ts` "the build runs under its Content-Security-Policy, with no violation" (both builds: login, fonts loaded, no `securitypolicyviolation`), the popout test checks its policy and console; the site's embedded demo e2e passes. Remaining: `'unsafe-inline'` styles allow CSS injection if DOMPurify were bypassed; a `<meta>` policy cannot set `frame-ancestors`, so that needs the header.
