# WP 6.4 — Act and adjudicate

**SRD ids:** Annex C PD6, PD7, PD8, PD9, PY-2 (act and adjudicate), PY-8, PY-9 (also PR2, ADM-44–46, PLY-53, PLY-56, D25, §3 rules 4 and 18) · **Depends on:** 6.3 · **Status:** done

## Goal

Scripts act and adjudicate (PY-2): they send text and templated messages, react to messages and phase changes, and the White Force proposes world states to the admin in a built-in umpire room (PD6, PD8, PY-8). The admin loads a proposal into the world-state draft after its change summary (ADM-46). An admin script writes on top of the draft without losing hand edits, and may, when the admin turns it on per script, publish without review (PD7, PY-9, PR2).

## Acceptance

- **Protocol 2** (`@wrx/schemas/bridge`, the JSON Schema export and the generated Python models). Version 1's read operations unchanged; added:
  - `sendMessage {roomId, text}` and `sendTemplate {roomId, templateId, values}`: only rooms the role can write; the advisory adjudication pause applies as in the composer (PLY-56), White Force exempt; the result is the stanza id.
  - `readDraft {}` and `writeDraft {state}`: admin only; the draft write replaces the stopgap `wrx_draft`.
  - `postProposal {state, summary}`: White Force roles that are not observers only; schema and 500 KB cap before posting (PLY-53); allowed in adjudication.
  - Events, delivered by the bridge while a run is active: `subscribeMessages {roomId}` and `subscribePhase {}`; in Python `game.on_message(room, handler)`, `game.on_phase(handler)`, and `await game.run_forever(seconds=None)`, which keeps the run alive, bounded by its time limit; a handler may call `game.stop()` to end it cleanly.
- **The umpire room (PD8, PY-8).** Room type `umpire`, one per game, made by the draft with the map room and created by publishing. Its participants are fixed (the design editor shows the room but cannot remove it or edit its members): the White Force as a write entry, so its roles that are not observers write and its observers read (rule 4), plus a read entry for each White Force observer that has assigned rooms elsewhere, so every White Force role sees it. Players of other forces have no access. Its observers are in the vault and revoked as for any read-only entry (ADM-37). Design check, publish planner, contract and publish tests on both backends, the data dictionary; SRD §3 rule 18 extended and a dated note in §14.
- **The proposal message (`world-proposal`).** Its own schema (`{state, summary}`), the 500 KB map-room cap, validated before posting and on receipt, accepted only in the umpire room and only from the admin or a White Force role. The admin's client shows it as a card with "Load into draft…", which shows the change summary first (ADM-46); every other client shows the card only.
- **Draft semantics (6.3's weak point).** A script's draft write is applied as the change from what it was based on (the draft it read with `readDraft`, else the published state at the run's start) onto the draft as it is when the run ends, so hand edits survive. After the run the panel shows what the script changed in the draft and how the draft now differs from the published state.
- **Opt-in publishing (PD7, PY-9, PR2).** The per-script `autoPublish` setting works for the admin's scripts: off by default; turning it on needs a confirmation that it changes the live map without review. A clean run that wrote the draft then publishes it at once, mid-phase included, after the same checks as a manual publish, and the publish is recorded with its change summary and the script's name where the admin sees it.
- **Runner timing (6.2's flaky tests).** A run's time limit starts when the script starts, not when the worker does; the probe canary listens on a free port. Root cause recorded.
- **PR previews and Pyodide (owner, Nov 6, 2026).** A PR preview includes `py/` only when the PR touches the runner, the SDK or Python files; the main site always does. Without it, the Scripts panel says it is unavailable in this build.
- **Tests:** unit and e2e on the mock (an admin script sends a message; a White Force script posts a proposal and the admin loads it; auto-publish on and off; an `on_message` handler reacts; the pause holds for a role outside the White Force; hand edits survive an admin script); contract tests for the umpire room on both backends; the ejabberd Playwright project if Docker runs.
- **Docs:** `docs/python-sdk.md` (writes, events, proposals), the site's umpire page, release notes.
- **Gates:** `pnpm check`, `pnpm check:python`, build and `check:bundle`, `CI=1 pnpm e2e` twice, `e2e:mock-host`, `e2e:admin-ui`, `e2e:theme`, the site build with `check:site` and `check:blog`, screenshots `--repeat`; on ejabberd the contract, publish and audit suites and the Playwright project, if Docker runs.

## Notes

- **Why the White Force as a force entry.** A role entry for a White Force observer assigns it (rule 4), limiting it to the rooms naming it; a force entry does not. So the umpire room names the White Force, and adds a role entry only for an observer already assigned elsewhere, for whom one more does not change its other rooms.

## Notes (done)

- **Protocol 2** (`@wrx/schemas/bridge`, `bridge-protocol.schema.json`, Python models regenerated). Version 1's nine read operations unchanged and first; added `sendMessage {roomId, text}` and `sendTemplate {roomId, templateId, values}` (→ `{stanzaId}`), `readDraft {}` (→ `{state, held}`: the draft, else the published state), `writeDraft {state}` (→ `{assets}`), `postProposal {state, summary}` (→ `{stanzaId}`), `subscribeMessages {roomId}` and `subscribePhase {}` (→ `{}`), the `paused` error code, and events `{type: 'message', message}` and `{type: 'phase', state}`. Requests carrying a world state may be 1,000,000 characters; the rest keep 10,000. Roles (`OPERATION_ROLES`): reads, sends and subscriptions for the admin and the White Force; `readDraft`/`writeDraft` admin only; `postProposal` White Force only. The stopgap `wrx_draft` is gone.
- **The bridge** sends through the store's own send paths (`{quiet: true}` keeps a refused script send out of the composer's unsent text): a room the role writes in, else `forbidden`/`not-found`; the adjudication pause for a role outside the White Force (`paused`, PLY-56), checked against `game-state` read for the call. Each run holds the rooms it sent in and its subscriptions until it ends (`beginRun`/`endRun`); message events are the room's messages after the subscription, in the protocol's form; phase events when the turn state changes. Events reach the worker as `event` messages and the script through `_wrx_bridge.next_event(timeoutMs)`, queued (1,000, oldest dropped) while the run lasts.
- **Python** (`wrx` 0.2.0): `send_message`, `send_template`, `read_draft`/`draft`, `write_draft`, `post_proposal`, `umpire_room`, `on_message(room, handler, include_own=False)` and `on_phase(handler)` (both decorators too), `run_forever(seconds=None)` and `stop()`, `PausedError`; `Bridge.next_event`. **How a run with handlers stays alive:** `await game.run_forever()` subscribes and waits; it returns after `seconds` or when a handler calls `stop()`, and the script then finishes cleanly; otherwise the run's time limit or Stop ends it, which is not a clean finish (an admin's draft write is dropped, PD9). A handler that raises ends the run. Messages under the script's own login are left out by default.
- **The umpire room.** Room type `umpire` (config `{}` only; chat text and proposals; no templates), one per game, added by the draft with the map room (`withUmpireRoom`) and so created by the next publish; the design editor shows it with its members read only and offers no delete, retype or participants. Fixed participants (`umpireParticipants`): each White Force as a write entry, plus a read entry for each White Force observer already assigned rooms elsewhere (see Notes). Its White Force observers are read-only through the vault as for any read-only entry (they are in it already). Design check: one umpire room, fixed participants, valid config. SRD §3 rule 19 states it; §14 has the dated note.
- **Proposals.** `world-proposal` `{state, summary ≤ 2,000}` with the 500 KB cap; the registry keeps it to the umpire room (chat rooms now take chat and template bodies only); the store accepts it only from the admin or a White Force role and posts it only for a White Force role that is not an observer (`sendProposal`, not paused). The umpire room's panel (`UmpirePanel`) is the chat panel with a proposal card; in the admin's own view the card has "Load into draft…": the change summary against the published state, a warning when the draft has unpublished edits (loading replaces the whole draft), then the proposal is the draft.
- **Draft semantics (decided).** A clean run's write is applied as the script's change from its base (the first `readDraft`'s state, else the published state at the run's start) on top of the draft as it is at the end of the run (`applyWorldChanges`), asset by asset; the turn follows the script only if it changed it. An asset both the script and a hand edit changed takes the script's values and is named. The panel shows what the script changed in the draft, what it overwrote, and how the draft differs from the published state. SRD PY-9 says so.
- **Publishing without review.** The per-script `autoPublish` works for admin scripts: off by default and for duplicates and imports; turning it on needs an inline confirmation ("It changes the live map without review…"). A clean run that changed the draft then publishes it as "Publish world state…" would (only if it differs, the current turn stamped, the 500 KB check, `sendWorldState`, the draft cleared), at any time, and records `{at, script, stanza id, turn, added/removed/changed titles}` in the admin account's private storage (`wrx-script-publishes`, newest 50), listed in the panel under "Published without review".
- **Timing tests (6.2), root cause.** `run()` started the PY-10 timer on call, before the worker was ready, and the worker then loaded the script's packages (pydantic, pandas) inside that window; under load, start-up and imports used up the e2e's 3 s. Now the worker posts `started` after its imports and the limit starts then; until then the start limit (60 s) applies and a script that never starts fails as such. The canary listened on PORT+1, which another server could hold; it now takes a port the system picks (`/__canary`). Committed alone (8141628), cherry-picked into PR #13 as 5a03f26.

## Weak points

- **The pause cannot be exercised by a browser script**: only the admin and the White Force run scripts (PD4), and both are exempt, so PLY-56's refusal is tested at the bridge with a fake store; it matters for a later native runner or automated players.
- **`run_forever` without `seconds` or `stop()` ends at the time limit**, which is not a clean finish, so an admin handler script's draft write is dropped; documented, but easy to trip on.
- **Dropped events are silent**: the worker counts them (`dropped_events`), but the SDK does not surface the count yet.
- **"Own" messages are the login's**: everyone sharing a role's login is "own" to `on_message`, and is left out by default.
- **The publish record is read then written** in private storage (no conditional write); two sessions recording at once keep the last writer's. It keeps the newest 50.
- **Publishing without review publishes the whole draft**, hand edits included, not only the script's change.
- **Loading a proposal replaces the whole draft** (with a warning) rather than merging.
- **Every existing game's next publish adds the umpire room**, a structural change that resets players' layouts once; the admin's and White Force's default layouts gain a room.
- **The act e2e ran on the mock only**; on ejabberd the umpire room ran at the transport and publish level, not through the panel. `sendTemplate` is covered by bridge and SDK unit tests, not an e2e.
- **The ejabberd Playwright project needs `--workers=1`** (CI's setting); with more workers it fails on the shared server.
- **One browser**: Chromium only here.
