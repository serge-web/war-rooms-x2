# S15: PubSub item timestamps and order on ejabberd 26.09

> **INTERNAL. Not for the public site (DOC-2).** This record covers PubSub server behaviour that the objectives access rules and the admin tooling depend on. Keep it, and the check id, out of the published docs and PR titles.

- **Date:** 2026-11-04 · **Server:** ejabberd 26.09, `ejabberd/ecs@sha256:8ebff5b2…98e0e` (the digest `deploy/ejabberd/compose.yaml` pins), reference config `deploy/ejabberd/ejabberd.yml` unchanged (spike config `ref`)
- **Evidence:** `spike/s15-s16/` (checks, stanzas, `results/s15-s16-run.jsonl`, run `final-20261104`). Every S15 check passes as recorded; the full contract suite (95 of 95), the R1 tests (20 of 20) and the deployment checks (5 of 5, one skipped: the served client) pass on the same stack.

## Question

Do PubSub items fetched with an items request (XEP-0060 §6.5), not only live events, carry a server timestamp that readers can order by? §3 rule 14 has each author of a force's objectives write its own item, because a publisher cannot overwrite another's item (S14-8), and readers show the newest "by server timestamp (the PubSub delay stamp)". §10's pass criterion: fetched items carry a server timestamp usable for ordering. If not: order by server item order, else fall back to `updatedAt`.

## Decision

1. **S15 fails. A fetched item carries no time.** An `<item/>` in an items reply has only `id` and `publisher` (the latter because the transport sets `pubsub#itemreply`), and the payload. There is no `<delay/>`, attribute or element with a time, in a full fetch, a `max_items` fetch, an RSM page or a fetch by id, before or after a restart. The service has no MAM for PubSub nodes and the server answers no XEP-0202 entity-time request (`service-unavailable` for both).
2. **The server's item order is creation order, not edit order.** ejabberd stores a `creation` and a `modification` time for each item (both in microseconds, in SQLite), but orders by `creation` only:
   - a full items request lists items oldest created first;
   - `max_items` N returns the N newest created, newest first;
   - RSM pages run oldest created first;
   - re-publishing an item updates its payload and its `modification` time, but does not move it.

   So "the newest by server order" is the newest *first publish of an id*. With fixed ids per author it is not the newest edit: after `admin`, `umpire`, `admin-2`, then an edit of `umpire`, `max_items` 1 returns `admin-2`. The order was the same across 80 items, back to back and 40 in flight at once (where it matched the order in which a subscriber was notified), and after a server restart.
3. **The only server times a client can see are not usable as the rule's timestamp:**
   - **RSM cursors.** A reply to a `max_items` or RSM request carries an RSM `<set/>` whose `<first/>` and `<last/>` are the *creation* times of the items at the page edges (`2026-11-04T07:45:43.920429Z`). XEP-0059 makes cursors opaque to clients, and they are creation times, so they say nothing about edits. A full fetch carries no `<set/>`.
   - **The last-item replay.** A node with `send_last_published_item` other than `never` replays, on subscribe, the item with the newest *edit*, with a `<delay stamp/>` of that edit. That is one item per node, only on subscribe, and the transport sets `never` so that events mean publishes (S6).
   - **Live events** carry no time; they arrive in publish order across publishers (contract S06).
4. **Recommended rule for §3 rule 14 (the §10 fallback, "server item order"): a new item per edit.**
   - Each save of an author's objectives publishes a **new item with a fresh id** (for example `<roleId>-<random>`), never re-publishing an old id.
   - The node keeps **`max_items` 1**. ejabberd trims per publisher (S14, S15-7), so each author keeps exactly its newest edit, and a retract notification goes out for the trimmed item.
   - Since every edit is a creation, creation order is edit order. **Readers show the last item of a full fetch, or the single item of `max_items` 1**; a later live item event replaces it. The author's `updatedAt` is for display only, never for ordering.
   - S15-8 checks this end to end: after edits by the admin, the umpire, the admin and the umpire twice, the node held one item per author in edit order each time, `max_items` 1 returned each newest edit, and the RSM cursors rose with each edit.
   - **Clean-up** when a role leaves the White Force or is deleted: the admin (owner) retracts the items whose `publisher` is that role's account. The owner may retract another publisher's item (S15-8).
   - If a later ejabberd trimmed the whole node rather than per publisher, `max_items` 1 would keep only the newest edit overall, which is still what readers show.
5. **Consequence for WP 5.8.** Rule 14 and the WP change from "one fixed item per author, newest by delay stamp" to "a new item per edit, newest by server order":
   - the domain reader (`latest` in `packages/domain/src/store.ts`, review F11) orders a fetch by position, not by `updatedAt`;
   - the admin tooling's objectives target (`OBJECTIVES_ADMIN_ITEM_ID`, one item id `admin`) and the audit change, since item ids are no longer fixed;
   - **the mock diverges from ejabberd and must follow it (ARC-11).** `packages/mock-server/src/pubsub.ts` lists items newest first, moves a re-published item to the newest place, and trims the node as a whole. ejabberd lists oldest created first, never moves an item, returns `max_items` as newest created first, and trims per publisher with a retract notification. No contract test covers fetch order today; WP 5.8 should move S15-2, S15-7 and S15-8 into the contract suite (they take only `ContractBackend` and `RawAccess`) and fix the mock to pass them.

## Method

Two publishers on one node: the admin (the node's owner) and `umpire`, a White Force editor with the `publisher` affiliation. A third account, `reader`, has the `member` affiliation and does every read. Each publisher publishes items with ids of its own. Every operation is a literal stanza sent through the contract suite's `RawAccess` over `wss://` and the real transport, so nothing in a client library can hide what the server sent (`src/checks/s15-timestamps.ts`).

**Node config**, as the transport writes it for an objectives node (`nodeConfigFields` in `packages/transport-xmpp/src/ejabberd.ts`), with `max_items` 10 (1 in S15-7 and S15-8):

```xml
<iq type='set' to='pubsub.localhost' id='…'><pubsub xmlns='http://jabber.org/protocol/pubsub'>
  <create node='RUN-objectives'/><configure><x xmlns='jabber:x:data' type='submit'>
    <field var='FORM_TYPE' type='hidden'><value>http://jabber.org/protocol/pubsub#node_config</value></field>
    <field var='pubsub#access_model'><value>whitelist</value></field>
    <field var='pubsub#publish_model'><value>publishers</value></field>
    <field var='pubsub#max_items'><value>10</value></field>
    <field var='pubsub#notify_retract'><value>true</value></field>
    <field var='pubsub#persist_items'><value>true</value></field>
    <field var='pubsub#deliver_payloads'><value>true</value></field>
    <field var='pubsub#notify_delete'><value>true</value></field>
    <field var='pubsub#send_last_published_item'><value>never</value></field>
    <field var='pubsub#itemreply'><value>publisher</value></field></x></configure></pubsub></iq>
<!-- then <affiliations>: umpire publisher, reader member -->
```

**Publish**, an objectives document as an XEP-0335 JSON payload:

```xml
<iq type='set' to='pubsub.localhost' id='…'><pubsub xmlns='http://jabber.org/protocol/pubsub'>
  <publish node='RUN-objectives'><item id='admin'><json xmlns='urn:xmpp:json:0'>
    {"schemaVersion":1,"text":"admin v1","updatedAt":"2026-11-04T07:45:41.669Z"}</json></item></publish></pubsub></iq>
```

**The sequence** (S15-1, S15-2, S15-6), 1.1 s between steps, so the steps differ even at one-second resolution:

1. the admin publishes `admin`;
2. `umpire` publishes `umpire`;
3. the admin publishes `admin-2`;
4. `umpire` re-publishes `umpire` (snapshot A);
5. the admin re-publishes `admin` (snapshot B).

After step 4 the four candidate orders all differ, so one fetch identifies the server's:

| Candidate | Order after step 4 |
|---|---|
| creation, oldest first | admin, umpire, admin-2 |
| creation, newest first | admin-2, umpire, admin |
| last edit, oldest first | admin, admin-2, umpire |
| last edit, newest first | umpire, admin-2, admin |

**Reads** at each snapshot: `<items node/>`, `<items node max_items='1'/>` and `'2'`, RSM pages of one (`<set xmlns='http://jabber.org/protocol/rsm'><max>1</max><after>…</after></set>`), and `<items node><item id='umpire'/></items>`. The stored `creation` and `modification` columns were read from the server's SQLite file with the image's `sqlite3 -readonly`, as evidence of what the order rests on; a client cannot see them.

**Other checks:** S15-3, 20 back-to-back publishes from each publisher, alternating, then a re-publish of every third, then 20 from each in flight at once, with `reader` subscribed; S15-4, a live event, and the last-item replay on subscribe from a node with `send_last_published_item` `on_sub`, after `umpire`, `admin`, then an edit of `umpire`; S15-5, `disco#info` of the service and the node, a MAM query to the node (`<query xmlns='urn:xmpp:mam:2' node='…'/>`), and XEP-0202 `<time xmlns='urn:xmpp:time'/>` to the server; S15-6, the S15 sequence, a server restart (same volume), then the same reads; S15-7, `max_items` 1 with both publishers; S15-8, the recommended rule.

## Weak points

- The order rests on ejabberd's choice of `creation` for sorting, which no XEP requires. S15-2 and S15-8, once in the contract suite, guard it across upgrades (NFR-22).
- `creation` is the server's wall clock. A server clock stepped backwards (a bad NTP correction) between two edits would put the later edit first until the next one. Low: one server, one clock, and the next edit corrects it.
- The rule leaves a window in which an author's old and new items both exist: none was observed (the trim happens in the publish), but a reader that misses the retract event, for example while reconnecting, still has the newer item last in its next fetch.
- RSM cursors were seen to be creation times; the rule does not use them, since XEP-0059 makes them opaque.
