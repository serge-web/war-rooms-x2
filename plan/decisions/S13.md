# S13: offline observer voice revocation (ADM-37), and the WebSocket message size limit (R15, PLY-53)

> **INTERNAL. Not for the public site (DOC-2).** This record covers access-control behaviour and its mitigations (R13–R15), admin-tooling rules (ADM-37, R-B) and server configuration. Keep it out of the published docs.

- **WP:** 0.1 · **SRD ids:** ADM-37, R15, PLY-53 (also D2, D8, D22, PLY-12, PLY-39, R1, R13, NFR-3, NFR-21, NFR-22)
- **Date:** 2026-10-24 · **Server:** ejabberd 26.09, `ejabberd/ecs@sha256:8ebff5b2…98e0e`, reference config from serge-web/xmpp-spike commit 4992530
- **Evidence:** `spike/s13/` (tests, stanzas, `results/s13-run.jsonl`). 27 of 27 tests pass on fresh volumes (`pnpm test`, 291 s).

## Decision

1. **ADM-37: S13 fails. Use the fallback, the encrypted observer-password vault.** No documented admin feature over XMPP can make a member observer a `visitor` before that observer has joined. The visitor role has to be stored while the observer is in the room, and putting it there needs the observer's own login. The only settings that make a user a default visitor need a room that is not members-only. That breaks room confidentiality: other forces and anonymous users can join and read, and anyone can read the archive. NFR-3 and NFR-21 rule that out.
2. **R15: the WebSocket listener has no message size limit.** No room message up to 64 MiB was refused, with or without `max_stanza_size`. ejabberd does not apply the c2s `max_stanza_size` to WebSocket sessions, and refuses the option on the `ejabberd_http` listener. The "~885 KB drops the connection" in R15 did not reproduce.
3. **PLY-53: cap each outgoing room message at 64 KiB**, that is 65,536 bytes of UTF-8 in the serialised stanza, and reject anything larger with a message. The cap is client-side only (see R15 below).

## Results per option

- the observer's first join is as `visitor`;
- its post is rejected and no other occupant receives it;
- this holds after a reconnect and after a server restart;
- no observer password and no REST were used;
- the positive control holds: a normal member can still post.

All options were settled within the time box; none is inconclusive.

**Not tested, outside the permitted command set:**

- MUC/Sub `subscribe_room`, which subscribes the observer to the room on its behalf;
- `muc_register_nick`, which registers its nick.

From the 26.09 source, a role change needs the target's current role to be `participant` (`can_change_ra/7`). A user who is not present has role `none`, so both would most likely end like option 1. MUC/Sub would also need `allow_subscription: true`, which the S1b hardening turns off.

**Why there is no admin route (ejabberd 26.09 `mod_muc_room.erl`).** The initial role on join comes from `get_default_role/2`, overridden by the stored role map only in moderated rooms. `get_default_role` is:

- `owner`/`admin` → `moderator`;
- `member` → `participant`;
- `outcast` → `none`;
- `none` → `visitor` only when the room is not members-only and `members_by_default` is false.

The stored map is written by `set_role/3`, which a role change reaches only if `can_change_ra` allows it, and that needs the occupant to be present with a role.

<iq type="set" to="ROOM@conference.localhost" id="…">

### Option 3 and NFR-22

`mod_adhoc_api` runs over XMPP ad-hoc commands, not HTTP, so NFR-22's ban on the REST `/api` and the web admin does not cover it. All three stacks return 404 for `/api` and `/admin` (`tests/no-rest.test.ts`).

Even so, the hardened reference removed the module on purpose: with `what: "*"` it exposes all 198 API commands to the admin JID, including accounts, sessions and `send_stanza`. Restricting `api_permissions` → `what:` to a list of command names works; the variant advertises exactly the five room commands. Since the module gives nothing for ADM-37, **keep it out of the reference deployment.**

## What the vault route means for the admin tooling (WP 2.1, also 2.3 and 2.10)

No WP 2.1 brief exists yet. These points belong in it.

1. **AdminOps keeps the password route for observers.** `addToRoom(observer)` does three things:
   - sets the `member` affiliation;
   - logs in as the observer with the password from the vault, joins, and has the admin set `visitor` by nick;
   - leaves.

   This is the spike's `revokeObserverVoice`, unchanged. The vault is the source of the password, in place of an argument.
2. **When the vault is needed:**
   - the first time an observer is added to each room;
   - after **any** affiliation change for an observer in that room (R-B). Re-setting the same affiliation keeps the role;
   - for the ADM-41 audit. The stored role is not visible through `get_room_options` or any other documented room command (the options have no role entry), so checking "observer voice" means joining as the observer.

   Without the vault passphrase, none of these can be done; the only way out is a password reset under ADM-26, which locks out every session of that role (D22).
3. **The vault holds observer passwords only.** A password reset (ADM-26) and a role deletion (ADM-39) must update the vault in the same operation. Otherwise the next re-application fails, and the audit fails too.
4. **There is a window between grant and revoke.** Once the `member` affiliation is set, an online observer session that joins before the revocation joins as `participant` and can post. AdminOps should:
   - apply the membership and the revocation back to back;
   - do both **before** publishing the game data that tells the observer's client about the room, so the client has no reason to join early.

   The ADM-41 audit then catches anything missed.
5. **Rooms stay moderated and members-only (R-C, NFR-3).** Option 4 shows that the tempting alternative, an open room where observers are default visitors, leaks the room to everyone.
6. **Contract tests for the mock:** the two role-change errors above, `Invalid affiliation` from the ad-hoc API, and the visitor `forbidden` error.

## R15: message size measurements

Each probe is one groupchat message, `<body>` of ASCII `x`, from a fresh sender connection, with a second member in the room as receiver. The sizes below are bytes of the whole stanza.

| Stack (c2s `max_stanza_size`) | Sender | Probes (stanza bytes → outcome, time) | Largest delivered | Refused |
|---|---|---|---|---|
| reference (262,144) | player (shaped) | 262,145 → delivered, 0.1 s; 2,097,290 → delivered, 36.5 s (raw); the same through StanzaJS → delivered, 36.6 s | 2,097,290 | none |
| reference | admin (unshaped) | 2 MiB, 4 MiB, 8 MiB, 16 MiB, 32 MiB, 64 MiB (67,109,002) → all delivered, the largest in 20.0 s | **67,109,002** | none found ≤ 64 MiB |
| wscap (65,536) | player | 65,537 → delivered; 2,097,290 → delivered, 36.4 s (raw), 36.6 s (StanzaJS) | 2,097,290 | none |
| wscap | admin | 2 MiB to 64 MiB doubling → all delivered, the largest in 22.5 s | **67,109,002** | none found ≤ 64 MiB |
| httpcap (`max_stanza_size: 65536` on `ejabberd_http`) | — | ejabberd does not start: `[critical] … Invalid value of option listen->2: Unknown option: max_stanza_size` | — | — |

- **Just over the limit:** there was no limit to go over. In every probe the message was delivered; no error stanza came back and the connection stayed open (`stanzas/r15-*-cap-plus-1.xml`, `stanzas/r15-*-admin-largest-delivered.xml`). Sizes above 64 MiB were not tried. Beyond about 100 MiB, the Node `ws` client's default `maxPayload` would cut the receiving side, and that is a client limit, not the server's.
- **What `max_stanza_size` does on WebSocket:** nothing. `ejabberd_http_ws` copies the c2s limits into the session, but parses each WebSocket message as a whole element (`fxml_stream:parse_element/1`), so the stream parser's size check never runs.
- **The only server-side lever is the shaper**, which limits rate, not size. Player messages above the 300 kB burst are slowed to 50 kB/s: a 2 MiB message held the sender's connection for about 36 s, and it was delivered.
- **The ~885 KB connection drop is not reproduced.** No 885 KB test was ever saved in the earlier spike. The 2 MiB raw and StanzaJS probes from a shaped player both went through.
- **Side effects of oversized messages:**
  - each is stored in MAM (SQLite) and sent to every occupant;
  - each is replayed in join history to everyone who joins. A probe sender's join pulled in several earlier multi-MiB messages.

## PLY-53: recommended client cap

**Rule: reject an outgoing room message when its serialised stanza is larger than 65,536 bytes in UTF-8.** Count the bytes after XML escaping, including any structured payload, not the JavaScript string length. The client shows a message and does not send. The mock enforces the same rule.

Why 64 KiB:

- It is ejabberd's documented recommended c2s `max_stanza_size`. If a future ejabberd starts enforcing the c2s limit on WebSocket (the reference sets 262,144), the client cap stays below it.
- It is far below the shaper's 300 kB burst, so a message at the cap goes out at once and does not stall the connection.
- It keeps MAM pages bounded: 50 messages × 64 KiB ≈ 3.2 MB at worst. Join history stays small too.
- For text it is roughly 16,000 characters in the worst case (4-byte UTF-8 characters, or many `<`/`&` characters that escape to 4–5 bytes), and far more for plain text. That is ample for chat.

PubSub items stay under the server's own 250 KB node cap, as PLY-53 already says.

**Residual risk (R15):** a modified client can still post room messages of at least 64 MiB. They are stored in MAM and fanned out. The mitigations are the shaper (rate) and `max_user_sessions: 10`. As a last resort the admin can destroy the room, which also deletes its archive (R-F, ADM-40). For an internal deployment that is the same posture the spike accepted. A hard cap would need a reverse proxy that limits WebSocket message size, or a server module, and D2 rules out the module.
