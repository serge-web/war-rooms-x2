# S14: collection-level PubSub access control (XEP-0248) on ejabberd 26.09

> **INTERNAL. Not for the public site (DOC-2).** This record covers PubSub access-control behaviour, a leak path in a naive layout, and server configuration. Keep it, and the spike id, out of the published docs and PR titles.

- **WP:** S14 · **SRD ids:** Annex B (AD2, AD3), TPL-10 (also D2, R14, NFR-16, NFR-22, ARC-10, ARC-11, ADM-36)
- **Date:** 2026-11-01 · **Server:** ejabberd 26.09, `ejabberd/ecs@sha256:8ebff5b2…98e0e` (the digest `deploy/ejabberd/compose.yaml` pins), reference config `deploy/ejabberd/ejabberd.yml` at commit 68b2535
- **Evidence:** `spike/s14/` (checks, stanzas, `results/s14-run.jsonl`). Final clean run `final-20261101`: every V0 check, the full contract suite (89 of 89) and the R1 tests (20 of 20) pass on V0; V1 and V2 do not start.

## Decision

1. **A node per asset under a collection is not possible on ejabberd 26.09 with standard controls.** XEP-0248 collections need the `dag` plugin and the `dag` node tree, and 26.09 has neither. At start-up ejabberd drops the plugin ("Plugin 'dag' of mod_pubsub is not supported anymore and has been automatically removed"). The image has no `nodetree_dag` module either, so `nodetree: dag` aborts the whole server, not only PubSub. V1 and V2 therefore never start, and S14-1 to S14-8 and S14-10 cannot run under them. Bringing `dag` back would take a custom build or an added module, which D2 and the pinned official image (NFR-22) rule out.
2. **The reference config looks as if it supports collections, but it does not.** It advertises `pubsub#collections` and accepts every XEP-0248 field: `pubsub#node_type=collection`, `pubsub#collection` on create and on configure, and the collection subscribe options. None of them has any effect. The "collection" is a plain leaf that takes items. `disco#items` lists no children. Leaves keep their own access model, so a leaf created with no access config is **open, readable and subscribable by any user, anonymous included**. Nothing is delivered through a collection subscription.
3. **By the decision rule, Annex B uses two nodes per force.** S14-2 to S14-7 fail.
   - Nodes: `force-assets:<forceId>`, the force's own assets, and `force-view:<forceId>`, what that force knows of other forces' assets.
   - Each is a flat whitelist node with one item per asset, item id the asset GUID (AD2).
   - AdminOps sets access by rule (R14), as it does for objectives.
   - S14-10 measured this layout with 600 assets; the numbers are below.
4. **Who can update an asset item (S14-8): only the account that last published it, or the node owner.**
   - A second publisher's overwrite and retract are refused with `<forbidden/>` (type `auth`).
   - The owner (the admin) can overwrite anyone's item. After that, the original publisher can no longer update it.
   - So with one item per asset, each asset has one writer at a time. The owner must choose the writer model (open question 1).
5. **The cost of enabling `dag`: it cannot be enabled.**
   - V1 and V2 do not start, so the contract suite and the R1 tests cannot run under them.
   - V0's database under V1 does not start either. Started under V0 again, its nodes, items and affiliations are intact.
   - Listing `dag` without the `dag` node tree is either harmless or breaks every node, depending on the plugin list:
     - with `[flat, dag, pep]` (probe V1p) ejabberd drops `dag` and runs exactly V0's PubSub; the suite passes 89 of 89 and R1 20 of 20;
     - with `[dag, pep]` (probe V2p) only `pep` is left, so the admin cannot create service nodes (`<forbidden/>` "You're not allowed to create nodes"); the suite and R1 fail completely (0 of 89, 0 of 20).
   - The reference config is unchanged.

### S14-5 without collections, for comparison

These are plain leaves. The admin creates each one as a whitelist node, makes blue a member, and subscribes blue to it (XEP-0060 §8.8.2), then publishes one item to each. This is the only way to get a node per asset on 26.09.

| Leaves | Create | Affiliate | Subscribe | Publish (32 in flight) | Delivered | p95 / max latency | Memory |
|---|---|---|---|---|---|---|---|
| 600 | 7.9 s | 7.2 s | 8.0 s | 8.8 s | 600 of 600, no duplicates | 503 / 636 ms | 87 → 90 MiB |
| 1,200 | 8.1 s | 4.2 s | 4.3 s | 6.5 s | 1,200 of 1,200, no duplicates | 186 / 269 ms | 89 → 94 MiB |

The 600-leaf row is from the final run, which shared the host with another stack. An earlier run on a quieter host gave 3.3 s, 1.9 s, 1.6 s and 2.9 s, with p95 178 ms. The figures are for one reader. Each further reader needs its own affiliation and subscription on every leaf. A login after the items exist got none of them pushed (`send_last_published_item` needs a presence subscription), so a client would fetch 600 nodes one by one. It works, but every reader costs 2 × 600 owner requests per force, there are 600 or more nodes per force to audit (ADM-41), and `disco#items` on the service lists every node name to anyone (S10), so the asset count and GUIDs would leak. **Not recommended.**

## S14-10: one node per force, 600 assets (the chosen layout)

Each item is a 242-byte asset with 12 attributes. One reader (`blue`) is a member and subscribed by the owner. `blue2` has the publisher affiliation.

| Measure | Result |
|---|---|
| Admin publishes 600 assets, 32 in flight | 4.4 s (136 items/s); 600 of 600 delivered once; p95 282 ms, max 353 ms |
| A player publishes 600 of its own items one at a time, through the player shaper | 4.6 s (130 items/s); 600 of 600 delivered; p95 15 ms |
| Retrieve everything in one request (1,200 items in the node by then) | 72 ms, one 329 KB stanza; no RSM unless asked |
| RSM pages of 50 (XEP-0059) | 25 pages, 1,200 items, no duplicates, 151 ms in all |
| One item by id | 2 ms |
| `pubsub#max_items` 1,200 or 1,500 | refused with `<resource-constraint/>` "Bad value of field 'pubsub#max_items'": the server cap `max_items_node` (stock 1,000) |
| Memory | 96 → 136 MiB over the whole check (the container) |

**`max_items` applies to each publisher, not to the node** (`node_flat` trims the publishing account's own items).

- `max_items` was 600, yet after 600 items by the admin, 600 by `blue2` and 400 more by the admin, the node held 1,200 items: the admin's newest 600 (200 old, 400 new) and all 600 of `blue2`'s.
- So a force with N assets needs a `max_items` of at least N for its single writer.
- More than 1,000 assets per writer needs `max_items_node` raised in the reference config. That is a standard option, but a config change (B2).
- The mock trims the node as a whole (`packages/mock-server/src/pubsub.ts`), which differs once two publishers together exceed `max_items`. Today no node reaches that. B2's contract tests should pin it down, or the mock should follow the server (ARC-11).

## What this means for Annex B and later WPs

- **AD2, AD3:** two flat whitelist nodes per force, with one item per asset and the asset GUID as item id. `force-view:<forceId>` holds copies that the umpire or a rule publishes. A force's awareness of another force's asset is therefore a copy that has to be kept up to date, not a view.
- **History** (open in Annex B) cannot come from items on per-asset nodes. It needs a third node per force or the MAM option (Annex B option 3).
- **Never rely on inheritance.** A leaf placed "in" a whitelist collection is open by default on this server. AdminOps must set `pubsub#access_model` and affiliations on every node it creates, as WP 2.1 already does. B2's audit should flag any asset node whose access model is not `whitelist`.
- **Contract tests for B1 and B2** (ARC-10). These move from `spike/s14/src/checks/` without change, since they take only the contract suite's `ContractBackend` and `RawAccess`:
  - S14-8: overwrite and retract refused, the owner's overwrite allowed, and the original publisher locked out afterwards;
  - S14-10: RSM paging over an asset node; `max_items` per publisher; the `max_items_node` cap refused with `resource-constraint`;
  - S14-1 to S14-7 as regression guards: if they turn green, a server upgrade added collections, and this record should be revisited.

## Open questions for the product owner

1. **Writer model (Annex B question 7, now sharper).** With one item per asset, only one account can update a given asset at a time. Should that be the admin and umpire only, one asset-owner role per force, or items per author with the newest shown (the objectives pattern, with its clock problems, F11)?
2. **Forces with more than 1,000 assets.** Are they needed? If so, the reference config's `max_items_node` must be raised (B2, with review).
3. **Visibility inside a view.** Every reader of a force's view node fetches all of it: one 330 KB response at 1,200 assets, or RSM pages. Visibility per asset within one force's view is not possible without a node per asset. Is per-force granularity enough?
4. **Awareness by copy.** Other forces' assets reach `force-view:<forceId>` only as copies published by the umpire or by rules. Who publishes them, and how stale may a copy be?
5. **History** (Annex B question 8): a third node per force, or MAM in a per-force room?
