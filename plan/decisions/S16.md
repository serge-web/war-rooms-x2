# S16: byte-rate shaping on the WebSocket listener, ejabberd 26.09

> **INTERNAL. Not for the public site (DOC-2).** This record covers the server's rate limits, what a modified client can still send, and server configuration. Keep it, and the check id, out of the published docs and PR titles.

- **Date:** 2026-11-04 · **Server:** ejabberd 26.09, `ejabberd/ecs@sha256:8ebff5b2…98e0e` (the digest `deploy/ejabberd/compose.yaml` pins); configs `ref` (the reference `deploy/ejabberd/ejabberd.yml`, unchanged), `tight` and `http` (below)
- **Evidence:** `spike/s15-s16/` (checks, stanzas, `results/s15-s16-run.jsonl`, run `final-20261104`). Every S16 check passes as recorded under `ref` and `tight`; on `ref` the full contract suite (95 of 95), the R1 tests (20 of 20) and the deployment checks (5 of 5, one skipped: the served client) pass.

## Question

Does an ejabberd byte-rate shaper throttle a client that sends large stanzas over the WebSocket listener? WP 0.1 (S13) found no size limit on WebSocket: `max_stanza_size` does not apply there, and room messages up to 64 MiB were delivered (R15). A shaper limits rate, not size, so §10's pass criterion is a throttle. If it passes, adopt it, as long as 500 KB map-room messages still go through comfortably (PLY-53, D25).

## Decision

1. **S16 passes. The reference config's shaper already throttles WebSocket senders, by bytes.** `shaper: player` (50,000 B/s, 300,000 B burst) applied through `shaper_rules: c2s_shaper` on the `ejabberd_c2s` listener reaches every WebSocket session, because `ejabberd_http_ws` takes its limits from the first c2s listener. A shaped player's single message past the burst is read at about 50 kB/s: 500 KB in 3.6 s, 1 MB in 13.3 s, 2 MB in 33.1 s, against a prediction of (bytes − burst) / rate of 4, 14 and 34 s. Below the burst (64 KiB, 300 KB) there is no delay. The admin, `none` in `c2s_shaper`, sends 2 MB in 0.5 s.
2. **The throttle follows the configured shaper, not the network.** Under `tight` (20,000 B/s, 20,000 B burst, nothing else changed) the same player took 0.7 s for 64 KiB, 4.0 s for 150 KB, 10.6 s for 300 KB and 27.1 s for 600 KB, against 0.08 s for 300 KB under `ref`. ejabberd's shaper averages its rate over reads rather than keeping an exact token bucket, so a sender runs somewhat ahead of the prediction at first (26 kB/s over 300 KB), and settles to the set rate on larger sends (21 kB/s over 600 KB).
3. **What it does and does not limit:**
   - It is **per connection**. Two sessions of one player, sending 1 MB each at once, both finished in 13.3 s: together about 105 kB/s. With `max_user_sessions: 10`, one account can push about 500 kB/s, after ten 300 kB bursts.
   - It **never refuses** a stanza. Every message was delivered whole to the other member, and the sender's connection stayed up. A ping sent behind a large message waited for it (32.7 s behind 2 MB), so a sender stalls only its own connection.
   - It is **inbound only**: what the server fans out to other occupants, and replays from MAM, is not shaped.
   - A shaper **cannot be set on the WebSocket listener itself**. With `shaper: c2s_shaper` on `ejabberd_http` (config `http`), ejabberd does not start: `Invalid value of option listen->2: Unknown option: shaper`. The c2s listener, bound to the container's loopback and never published, stays the only place for it (WP 3.3).
4. **Adopted as it stands: no config change.** The shaper has been in the reference config since WP 3.3, and the deployment checks ("per-player rate limit (NFR-22)") already measure it on every stack in CI. A tighter shaper would not cap size either, and would slow the 100 kB PubSub items and the large first loads that the 300 kB burst was set for. `deploy/wrx1` and `deploy/ejabberd` are unchanged, so the contract suite needed no re-run for a config change; it was run on the spike's `ref` stack anyway and passes.
5. **500 KB map-room messages are comfortable.** Only the admin posts world state (D25), and the admin is unshaped: 500 KB in 0.14 s. A player's 500 KB message, which clients ignore in the map room, takes about 3.6 s, so the shaper would not block one either.
6. **Consequence for R15.** The mitigation is a byte-rate limit on WebSocket, not a count of messages as R15 says: a modified client can still post messages of any size, but at about 50 kB/s per connection (500 kB/s per account). A 64 MiB message from a player would hold its connection for about 22 minutes. R15 stays medium and accepted for v1; the residual risk is now slow large messages, stored in MAM and fanned out, rather than fast ones. The admin can end the sessions (`endUserSessions`) or destroy the room (ADM-40).

## Method

Each probe is one groupchat message of an exact size (bytes of UTF-8 in the serialised stanza), sent raw through the contract suite's `RawAccess` over `wss://` from a fresh connection, so its shaper bucket starts full (`src/checks/s16-shaper.ts`). The room is created by the admin per probe as a game room: members-only, moderated, persistent, archived, non-anonymous, side channels closed; the sender and `reader` are members, and `reader` is in the room. Times run from handing the stanza to the socket to the sender's reflected copy and to the reader's copy. A ping (XEP-0199) is sent right behind each message.

```xml
<message xmlns='jabber:client' to='RUN-player-500000@conference.localhost' type='groupchat' id='s16-500000-…'>
  <body>S16:s16-500000-…:xxxx…xxxx</body></message>          <!-- padded to exactly 500,000 bytes -->
<iq xmlns='jabber:client' type='get' to='localhost' id='s16-500000-…-ping'><ping xmlns='urn:xmpp:ping'/></iq>
```

**Configs.** Each is `deploy/ejabberd/ejabberd.yml` with a header and at most one change, written by `docker/make-configs.sh` and checked by `tests/startup/configs.test.ts`:

```yaml
# ref: the reference, unchanged. The parts that matter:
listen:
  - port: 5222
    ip: '127.0.0.1'
    module: ejabberd_c2s
    max_stanza_size: 262144
    shaper: c2s_shaper
    access: c2s
    starttls_required: true
  - port: 5443
    module: ejabberd_http
    tls: true
    request_handlers:
      /ws: ejabberd_http_ws
      /: mod_http_fileserver
shaper:
  player:
    rate: 50000
    burst_size: 300000
shaper_rules:
  max_user_sessions: 10
  c2s_shaper:
    none: admin
    player: all

# tight: only these two lines differ
    rate: 20000 # S16 tight (reference: 50000)
    burst_size: 20000 # S16 tight (reference: 300000)

# http: only this line is added, under `module: ejabberd_http`
    shaper: c2s_shaper # S16 http probe (reference: no shaper on this listener)
```

**Probes:** S16-1, the player at 64 KiB, 300 KB, 500 KB, 1 MB and 2 MB (`tight`: 64 KiB, 150 KB, 300 KB, 600 KB); S16-2, the admin at 500 KB and 2 MB (`tight`: 500 KB); S16-3, two sessions of the player, 1 MB each at once; S16-4, start-up of `http` on a fresh volume.

## Proposed changes

- **Config:** none. Keep `shaper: player` at 50 kB/s with a 300 kB burst and `c2s_shaper: none: admin, player: all` on the loopback c2s listener (`deploy/ejabberd/ejabberd.yml`, used by both `deploy/ejabberd` for CI and `deploy/wrx1`).
- **Tests (optional, a later WP):** the deployment check measures 40 writes of 25 kB. A single 600 KB stanza from a player taking more than about 4 s would pin S16's case, one large stanza, in CI as well. The spike's S16-1 does that today.

## Weak points

- The shaper is per connection, so the account-wide rate is set by `max_user_sessions` (10), not by the shaper alone.
- Anonymous sessions are shaped as `player` (`player: all`), but they cannot post to rooms (S10), so this matters only for what they may send to the server.
- The measured rate is ejabberd's averaging shaper on loopback, with the client sending as fast as it can. Over a slow network the sender's own uplink may be the limit first.
- A modified client is still not size-capped (R15): the shaper bounds how fast a large message arrives, not whether it is stored and fanned out.
