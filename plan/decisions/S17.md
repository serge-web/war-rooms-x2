# S17: Pyodide in a Web Worker, offline, under the client's Content-Security-Policy

> **INTERNAL. Not for the public site (DOC-2).** This record covers the client's security policy, what a script in the browser can reach, and how the sandbox is closed. Keep it out of the published docs and PR titles.

- **Annex:** SRD Annex C (after v1) · **SRD ids:** Annex C spike S17, PD3, PD4, PD6, PD7, PD9, PY-1, PY-3, PY-4, PY-5, PY-8, PY-10, PR3, PR4 (also D25, D26, ADM-44–46, NFR-7, ARC-6)
- **Date:** 2026-11-06 · **Pyodide:** 314.0.7 (CPython 3.14.2, Emscripten 5.0.3), npm `pyodide@314.0.7` and the release `pyodide-314.0.7.tar.bz2` · **Browser:** Playwright 1.63's Chromium, headless
- **Evidence:** `spike/s17-pyodide/` (page, worker, bridge, spec, `results/*.json`). The spec's 7 tests pass (`CI=1 pnpm test` there, 3.1 min). The app is untouched: `apps/web`, its build and `check:bundle` do not change.

## Question

Is the browser runner of Annex C (PD3) viable? Pyodide in a dedicated Web Worker, served entirely from our own build for an air-gapped install (NFR-7, PY-5), under the client's policy (PR3), reading the world state and a room's messages and writing a world-state draft or a White Force proposal through a bridge that offers only the SDK's operations (PY-4), with the draft applied only when a script finishes (PD9). How big is it, how long does it take to start (PR4), and can typed models generated from the JSON Schema export (ARC-6) run in it (PY-1)?

## Decision

1. **S17 passes, with conditions.** Pyodide runs in a module worker, offline, under the app's policy plus `'wasm-unsafe-eval'` only; the round trip works on the mock; a script cannot reach the network, storage or other contexts once the worker is locked down **and** the worker itself is under that policy. The conditions are items 4, 5 and 6 below; each is a small, known change for WP P2.
2. **Offline: yes, entirely from the build.** The core comes from npm (`pyodide`, 13.9 MB unpacked, the same files as the release's core); pandas, numpy and pydantic are not on npm and come from the full release (fetched here through the environment's proxy: 337.5 MB `.tar.bz2`, 380.6 MB extracted, 421 files, 357 packages). The spike ships only what it needs, sha256-checked against the release's lock file, with the lock trimmed from 111 KB to 3.3 KB so nothing else is installable. The run made 18 requests, all to its own origin, none to the canary on another origin. Pyodide's only CDN default (`cdnUrl`, jsDelivr) is used only under Node; in a browser every file resolves against `indexURL`/`packageBaseUrl`. micropip is not shipped.
3. **Sizes** (raw / gzip -9 / brotli -11, MB; `results/sizes.json`):

   | What | Files | Raw | gzip | brotli |
   |---|---|---|---|---|
   | Core | `pyodide.mjs` 0.02, `pyodide.asm.mjs` 1.25, `pyodide.asm.wasm` 9.60, `python_stdlib.zip` 2.55, lock 0.003 | **13.42** | 6.37 | 5.44 |
   | numpy | `numpy-2.4.6` wheel | 2.96 | 2.93 | 2.91 |
   | pandas + numpy | pandas 3.0.2 (4.18), numpy, python-dateutil (0.23), pytz (0.51), six (0.01) | 7.89 | 7.69 | 7.58 |
   | pydantic | pydantic 2.12.5 (0.46), pydantic_core 2.41.5 (1.31), typing-extensions, typing-inspection, annotated-types | 1.84 | 1.83 | 1.82 |
   | **Core + pandas** | | **21.31** | 14.05 | 13.02 |
   | Core + pandas + pydantic (everything shipped) | 15 files | 23.15 | 15.89 | 14.84 |
   | Spike's own scripts | worker 4.3 kB; page 351 kB (the mock, domain and schemas, which the app already has) | | | |

   Wheels are zip files and do not compress further; only the interpreter (`.wasm`, 9.6 → 3.6 MB gzip) gains from a compressing server. PR4's "pandas adds tens" is too high: pandas with numpy adds 7.9 MB.
4. **Content-Security-Policy: `'wasm-unsafe-eval'` is enough; `'unsafe-eval'` is not needed.** Results by policy (`results/csp.json`), each the app's own (`contentSecurityPolicy(false)` in `apps/web/vite.config.ts`) with one change, sent as a header on every response, as the reference deployment does:

   | Policy | core | numpy | pandas | pydantic |
   |---|---|---|---|---|
   | the app's, unchanged | fails: `script-src` violation `wasm-eval` | — | — | — |
   | + `'wasm-unsafe-eval'` | ok | ok | ok | ok |
   | strictest tried: `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; object-src 'none'; base-uri 'self'; form-action 'none'` | ok, no violation | ok | ok | ok |
   | + `'unsafe-eval'` instead | ok | ok | ok | ok |
   | + `'wasm-unsafe-eval'`, `.wasm` served as `application/octet-stream` | fails | — | — | — |

   - `script-src 'self' 'wasm-unsafe-eval'`: the interpreter and every shipped package's native module compile under it. No side module needed Emscripten's `EM_ASM` `eval`.
   - `worker-src 'self'` for a worker loaded from its URL; `'self' blob:` for the `blob:` bootstrap of item 5.
   - `connect-src 'self'`: Pyodide fetches the `.wasm`, the standard library, the lock file and each wheel; it also imports `pyodide.asm.mjs` (`script-src 'self'`).
   - **MIME type, a deployment condition:** Pyodide uses `WebAssembly.instantiateStreaming` with no fallback, which needs `application/wasm`. The reference config's `mod_http_fileserver` `content_types` (`deploy/ejabberd/ejabberd.yml`) has no `.wasm` entry, so it would need `.wasm: application/wasm` (and `.whl`, `.zip`: `application/zip`). This is from the config and the octet-stream test above; it was not run against ejabberd (no Docker daemon in this container).
5. **A worker's policy comes from its own script's response, not from the page's `<meta>` tag.** This matters for every host that cannot set headers, including the GitHub Pages demo and previews:
   - Under a header policy, the worker gets it: `eval`, `new Function` and `import()` of a foreign URL all fail.
   - Under a `<meta>`-only policy, a worker loaded from its URL has **no policy at all**: from Python, `call.constructor("return import('http://other-origin/…')")()` reached the canary on another origin, even with the lockdown in place.
   - A worker created from a `blob:` URL inherits the page's policy, `<meta>` included, and the same probe is refused. The runner creates the worker from a one-line `blob:` module that `import()`s the real worker; the page's policy then needs `worker-src 'self' blob:`.
6. **The worker and the bridge (PY-4): what leaks, and how each is closed.** Probes from Python, by case (`results/isolation.json`):

   | Probe from Python | No policy, no lockdown | Header policy only | Header policy + lockdown | `<meta>` only + lockdown, worker from URL | `<meta>` only + lockdown, worker from `blob:` |
   |---|---|---|---|---|---|
   | `import js` → `self`, `fetch`, `XMLHttpRequest`, `WebSocket`, `indexedDB`, `caches`, `importScripts`, `postMessage`, `BroadcastChannel`, `location` | all reached | all reached | all gone | all gone | all gone |
   | `pyodide.http.pyfetch`, `open_url` (another origin) | reached | refused by `connect-src` | gone (no `fetch`, `XMLHttpRequest`, `AbortController` in `js`) | gone | gone |
   | the same, own origin outside `pyodide/` | reached | **reached** | gone | gone | gone |
   | `run_js("globalThis")`, `new Function` | reached | refused (no `'unsafe-eval'`) | refused | **`new Function` reached the global scope** | refused |
   | `import()` of another origin, via `new Function` | reached | refused | refused | **reached** | refused |
   | then `fetch`, `indexedDB`, `postMessage`, `navigator.storage` on that global scope | reached | — | — | gone; `fetch` limited to `pyodide/` | — |
   | Emscripten `FS.filesystems.IDBFS.indexedDB()` | reached | **reached** | gone | gone | gone |
   | `pyodide_js.loadPackage("micropip")`, `import micropip` | not shipped | not shipped | not shipped | not shipped | not shipped |
   | `pyodide_js.loadPackage(<URL on another origin>)` | fetched | refused | refused | refused | refused |
   | `import pyodide_js` (the Pyodide API) | reached | reached | **reached** (harmless after the lockdown) | reached | reached |
   | walk of every JS object reachable from `pyodide_js`, `js` and the bridge (up to 4,000 objects, depth 5) | finds the global scope | finds it | none found (598 visited) | none found | none found |
   | requests to the canary origin | 6 | 0 | 0 | **1** | 0 |

   - **Header policy alone does not isolate.** Same-origin storage and messaging stay open: `indexedDB` (where the mock and the admin's draft live), `BroadcastChannel`, `caches`, a same-origin `fetch`. Hence the lockdown.
   - **The lockdown** (in the worker, after Pyodide and the packages load, before any script): Pyodide's `js` module is a frozen object holding only `setTimeout`/`clearTimeout` (`jsglobals`), not the global scope; `fetch`, `XMLHttpRequest`, `WebSocket`, `WebTransport`, `EventSource`, `importScripts`, `indexedDB`, `caches`, `BroadcastChannel`, `Worker`, `postMessage`, `MessageChannel` and others are deleted from the global scope and every prototype, and `navigator.storage`/`locks`; `fetch` is put back as a GET of files under `pyodide/` only, so `import pandas` still loads the shipped wheel (PY-3); the bridge keeps a private `postMessage`.
   - **The lockdown cannot remove `eval`, `Function` or `import()`.** Only the worker's policy does: by header, or by the `blob:` bootstrap under a `<meta>` policy. Both together close every probe.
   - **The bridge is the boundary.** Only strings cross: operation name and JSON in, JSON out; Python never holds a proxy of a page object. The page parses every worker message against a schema (a forged message from the unlocked baseline was dropped). Each call is checked against the role: unknown operations, `writeDraft` by the White Force, `postProposal` by the admin, a room the role does not have, invalid JSON and an invalid world state (zod `worldStateSchema` and the 500 KB cap, PLY-53) were all refused (`results/round-trip.json`).
7. **Round trip on the mock (PD6, PD7, PD9).** On the demo game in the in-tab mock server, with an admin and a White Cell session (`packages/domain` store):
   - The admin's script read Blue HQ's three messages, read the world state, moved 1st Rifles and wrote the draft. The draft was applied when the script finished, and `diffWorldStates` (`packages/domain/src/world-draft.ts`) showed "Changed: 1st Rifles (lat, lon)".
   - White Cell's script set Tank Company to damaged at 40% health and posted it to an umpire room the spike adds (PD8 is not in v1). The admin's session received it, validated it, loaded it into the draft with one action, and the summary showed "Changed: Tank Company (state, health)". White Cell's run wrote no draft.
   - **PY-8 needs its own message type.** The spike posts the proposal as chat text, and chat text is capped at 8,000 characters (`LIMITS.messageTextChars`). The six-asset sample took 1,724 characters, so about 28 assets fit, against the world state's 5,000 assets and 500 KB. The umpire room needs a proposal body type with the map room's 500 KB cap (PLY-53), as PY-8 implies.
8. **Stop, time limit and failure leave the draft as it was (PD9, PY-10).** The draft is held per run on the page and applied only on a clean finish:
   - **Time limit:** a script that wrote the draft and then awaited forever timed out at 1.5 s.
   - **Stop:** a script that wrote the draft and then spun in `while True: pass` was stopped from the page after 1 s.
   - **Failure:** a script that wrote the draft and then raised.
   - In all three the draft was unchanged; the same script finishing applied it.
   - Stop terminates the worker. Pyodide's interrupt buffer needs `SharedArrayBuffer`, which needs cross-origin isolation (COEP) that the client does not have. The next run starts a new worker: 1.8 s.
9. **Timings** (`results/timings.json`). Five samples each, medians.
   - **Machine:** a CI-like container (4 vCPU, 15 GiB, headless Chromium, loopback HTTP, no network latency).
   - **Cold:** a new browser context, empty cache. **Warm:** the same context, reloaded; the HTTP cache revalidates with `no-cache` and ETag, as the reference deployment's headers do.

   | | Cold | Warm |
   |---|---|---|
   | Worker ready (from `new Worker` to Python initialised, core only) | 1,800 ms | 1,830 ms |
   | First run of a small script (reads the world state through the bridge) | 10 ms | 10 ms |
   | First run that `import pandas` and builds a DataFrame of the assets | 3,240 ms (750 ms fetch and unpack, the rest the import) | 3,240 ms |
   | The next pandas run | 1–2 ms | 2 ms |
   | WebAssembly memory, core / after pandas | 30 MB / 75 MB | 30 MB / 75 MB |

   - A warm start is no faster than a cold one: on loopback the download is not the cost. Compiling and initialising the interpreter is (Chromium does not reuse compiled WebAssembly across these loads).
   - Over a real network add the download: 13.4 MB for the core (6.4 MB if the server compresses), 7.9 MB for pandas with numpy.
   - Pyodide's memory snapshot (`_makeSnapshot`/`_loadSnapshot`, marked experimental) might cut the start; not tried.
   - PR4 holds: seconds, fine for adjudication and analysis, not for interactive use. Start the worker when the script panel opens (PY-5), not at the first Run.
10. **Typed models (PY-1): yes, with pydantic.** datamodel-code-generator 0.90.0 turned `docs/json-schema/world-state-message.schema.json` into pydantic v2 models and into plain dataclasses (`spike/s17-pyodide/models/`). Pyodide ships a compiled `pydantic_core` (2.41.5) and pydantic 2.12.5 (1.84 MB with dependencies).
    - **pydantic:** in the worker, the generated models validated the live world state (6 assets) and refused one with `lat` 200 at `content.assets.<id>.lat`. `model_dump(mode="json")` round-tripped to the same JSON. Run 845 ms, of which loading pydantic 308 ms.
    - **Dataclasses:** carry the shape only. They accepted `lat` 200, so they are a fallback, not validation.
    - **Gaps found in the export:**
      - The asset model is named `Assets`, after the `additionalProperties` it came from: name it with a `$defs` entry or a title.
      - The 5,000-asset limit and "each asset keyed by its own id" are not in the JSON Schema; only zod checks them.
      - Chat and template message bodies are not exported, so the read layer's message models (P1) need them added to `JSON_SCHEMA_EXPORTS`.

## Method

- **Page and build.** `spike/s17-pyodide` is its own Vite page and build, outside the workspace, with its own dependencies (`pyodide` 314.0.7, `vite` 8.3.5, `zod` 4.6.7, installed with `--ignore-workspace`). It imports `packages/domain`, `packages/mock-server` and `packages/schemas` by relative path.
- **Pyodide files.** `scripts/fetch-packages.ts` fetches the ten wheels from the release (jsDelivr mirror, or an extracted release tarball for an air-gapped build) and checks each sha256 against the lock file. `vite.config.ts` copies them and the core into `dist/pyodide/`.
- **Server.** `scripts/serve.ts` serves `dist/` under a policy named in the path, with the reference deployment's other headers (`nosniff`, `no-cache` with ETag, `Cross-Origin-Opener-Policy`), `report-uri` for violations, and a canary server on another origin that counts requests.
- **Spec.** `tests/s17.spec.ts` drives the page through `window.s17`, writes each measurement to `results/`, and asserts it. `tests/probes.py` is the Python that probes the worker. `scripts/sizes.ts` measures the files.

## Recommended WP sizing (FT-4, numbered once the owner approves)

- **P1, SDK models and the read layer:** medium.
  - Generate pydantic models in CI from `JSON_SCHEMA_EXPORTS`, with named definitions.
  - Export the chat and template bodies.
  - The read operations, and the pandas helpers loaded on use.
- **P2, the browser runner:** large. Split it in two:
  - **P2a, runner and packaging:** the worker, lockdown, bridge and `blob:` bootstrap as a lazy chunk; the build step that fetches and checksums the wheels; the policy change for every role's client (PR3, decided) in `apps/web/vite.config.ts`, `app.test.ts`, `deploy/ejabberd/ejabberd.yml` with `.wasm`, and `tools/deploy/reference-config.test.ts`; a check that the main bundle does not grow; the probes of this spike as a regression test.
  - **P2b, the panel:** the script panel, the editor, Run and Stop with a time limit, output, private storage, export and import.
- **P3, act and adjudicate:** medium to large.
  - The proposal message type and the built-in umpire room (design, publish, membership; PD8, PY-8).
  - Send and react operations.
  - Opt-in publishing, recorded (PY-9).
- **P4, acceptance:** medium. The scenario, performance budgets from item 9, accessibility of the panel, a security review of the sandbox (this record's table as its starting point), docs.
- **P5, the native runner:** large. A Python XMPP client, the same SDK surface, and the contract suite run in both runners (PY-12).

## Weak points

- **One browser.** Chromium only. WebKit is not installed in this container, and the spike never installs browsers. Safari's handling of `wasm-unsafe-eval` and of `blob:` worker policy inheritance is untested. Firefox was not tried.
- **Not run against ejabberd.** The ejabberd stack was not run (no Docker daemon here). The header policy and MIME behaviour are emulated by `scripts/serve.ts` from the reference config, not observed from `mod_http_fileserver`.
- **The escape search is a sample, not a proof.** The object-graph walk is bounded (4,000 objects, depth 5, 200 names each). The lockdown is a deny-list of globals, so a new browser API would need adding. The real guarantees are the worker's policy (no `eval` or `import()`) and the bridge's validation; the lockdown narrows what is left.
- **`pyodide_js` stays reachable.** A script can call the Pyodide API itself, for example to replace `_wrx_bridge` or load another shipped package. It harms only its own run; the bridge never trusts the worker.
- **Timings are optimistic.** They are on loopback, on a 4-vCPU container. A slow machine, or a network instead of loopback, adds time. Memory is the WebAssembly heap only, not the worker's JavaScript heap.
- **The proposal is not the real thing.** It is chat text with a prefix in a spike-only room. The real umpire room and message type are P3 work.
- **One version.** Pyodide 314.0.7 pins CPython 3.14 and its wheel ABI (`pyemscripten_2026_0`). An upgrade replaces every wheel together.
